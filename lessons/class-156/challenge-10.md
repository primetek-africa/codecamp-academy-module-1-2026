# SQL Trigger Challenge 10: Airline Reservation System

## Introduction

In this challenge, you will work with the Airline Reservation System
database developed throughout the database course. You have already
worked with database design, normalization, primary keys, foreign keys,
constraints, CRUD operations, joins, advanced queries, views, stored
procedures, and PostgreSQL.

In this activity, you will apply these concepts to one of the most
important features of PostgreSQL: **database triggers**.

A trigger allows the database to automatically execute a function when a
specific event occurs on a table. This makes triggers useful for
implementing business rules, validating data, protecting the integrity of
the database, auditing changes, and automating database operations.

You have already analyzed several trigger examples in this project,
including passenger and pilot age validation, automatic reservation dates,
flight status validation, flight capacity validation, duplicate
reservations, reservation auditing, and protection of completed flights.

For this challenge, you will design and implement a **new trigger from
scratch**.

## Challenge 10: Protect Ticket Information

### Business scenario

In an airline reservation system, a ticket represents a completed
commercial transaction associated with a reservation.

Once a ticket has been created, some of its information should not be
changed arbitrarily. In particular, the system must protect the
**reservation associated with the ticket**.

The database already contains the following relationship:

```text
reservation
     |
     | 1 : 1
     v
ticket
```

The `ticket` table contains:

```text
id_ticket
number_ticket
reservation_id_ticket
purchase_date_ticket
price_ticket
payment_status_ticket
```

The `reservation` table contains:

```text
id_reservation
date_reservation
seat_number_reservation
status_reservation
passenger_id_reservation
flight_id_registration
```

Your task is to create a trigger that prevents a ticket from being
associated with a different reservation after the ticket has been
created.

---

## Objective

Create a PostgreSQL trigger that prevents the value of
`reservation_id_ticket` from being changed after a ticket already exists.

For example, if the database contains:

```text
Ticket 15 → Reservation 25
```

the following operation must be rejected:

```sql
UPDATE ticket
SET reservation_id_ticket = 30
WHERE id_ticket = 15;
```

The database should raise an exception explaining that the reservation
associated with an existing ticket cannot be changed.

---

## Requirements

Your solution must contain the following components.

### 1. Trigger function

Create a function named:

```text
fn_protect_ticket_reservation
```

The function must:

* Return `TRIGGER`.
* Use the `plpgsql` language.
* Use `OLD` and `NEW`.
* Compare the old and new reservation identifiers.
* Raise an exception when the reservation is changed.
* Return `NEW` when the modification is valid.

---

### 2. Trigger

Create a trigger named:

```text
trg_protect_ticket_reservation
```

The trigger must:

* Execute before an update.
* Execute for every affected row.
* Be associated with the `ticket` table.
* Execute the function created in the previous step.

The expected structure is:

```text
UPDATE ticket
      |
      v
BEFORE UPDATE TRIGGER
      |
      v
fn_protect_ticket_reservation()
      |
      +---- reservation changed?
      |          |
      |          +---- YES → RAISE EXCEPTION
      |
      +---- NO → RETURN NEW
```

---

## 3. Error message

When a user attempts to change the reservation associated with a ticket,
your trigger must raise an exception.

The message should clearly communicate the problem.

For example:

```text
Cannot change the reservation associated with an existing ticket
```

You may create your own professional error message as long as it clearly
describes the problem.

---

## 4. Test your trigger

You must provide SQL statements that demonstrate that your trigger works.

Your tests must include at least the following scenarios.

### Test 1: Valid update

Modify another ticket attribute without changing the reservation.

For example:

```sql
UPDATE ticket
SET price_ticket = 250.00
WHERE id_ticket = 1;
```

This operation should succeed.

---

### Test 2: Invalid update

Attempt to change the reservation associated with the ticket.

For example:

```sql
UPDATE ticket
SET reservation_id_ticket = 2
WHERE id_ticket = 1;
```

This operation should fail and display the exception generated by your
trigger.

---

### Test 3: Verify the original value

After the failed update, verify that the original reservation remains
associated with the ticket.

Use a `SELECT` query to demonstrate that the database maintained the
original value.

---

## Important concepts

Your solution should demonstrate that you understand the difference
between `OLD` and `NEW`.

For an `UPDATE` operation:

```text
OLD → values before the update
NEW → values after the update
```

For example:

```text
Before:

Ticket 1
Reservation 10

        UPDATE

After:

Ticket 1
Reservation 20
```

The trigger should compare:

```text
OLD.reservation_id_ticket
```

with:

```text
NEW.reservation_id_ticket
```

and reject the operation when they are different.

## Restrictions

For this challenge:

* Do not modify the database structure.
* Do not remove the foreign key from `ticket`.
* Do not remove the `UNIQUE` constraint.
* Do not solve the problem using application code.
* The validation must be performed by a PostgreSQL trigger.
* Do not modify existing triggers to solve the challenge.
* Create a new trigger function and a new trigger.
* Use `RAISE EXCEPTION` for the invalid operation.

## Bonus Challenge

Extend your trigger so that the ticket's **price cannot be changed after
payment has been completed**.

Use the `payment_status` table to determine whether the payment has been
completed.

The trigger should allow:

```text
Pending → price can be modified
Paid    → price cannot be modified
```

If a user attempts to modify the price of a paid ticket, the trigger
should reject the operation with an appropriate exception.

This bonus challenge requires you to work with:

* `OLD`
* `NEW`
* Conditional logic
* `SELECT ... INTO`
* Foreign key relationships
* Business rules
* `RAISE EXCEPTION`
* PostgreSQL triggers

## Learning objective

The purpose of this challenge is not simply to create another trigger.
The goal is to understand how database-level business rules can protect
data even when an operation is performed directly against PostgreSQL.

A well-designed database should not depend exclusively on the backend
application to protect critical business rules. The database should also
enforce the rules that guarantee data integrity.

By completing this challenge, you will practice designing a trigger,
implementing it with PL/pgSQL, testing both valid and invalid operations,
and explaining how `OLD` and `NEW` allow a trigger to inspect changes made
to a database record.
